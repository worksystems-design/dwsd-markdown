# DWSD format 1.10 — guide for agents

Read this before you create or change an entity. A DWSD organization is a folder of
Markdown files.

## Rules

- **One file = one entity.** YAML frontmatter between `---` lines, then a Markdown body. `type:` decides the type, not the folder; each type lives in one flat plural folder (below). Files are UTF-8.
- **The file name is the identity** and the display label: `Jonas Keller.md` is `[[Jonas Keller]]`. Spaces are fine. Renaming a file renames the entity, so update every link to it.
- **Keys are kebab-case** (`for-domain`, `unit-type`). `<base>-type` keys (`unit-type`, `agreement-type`, `interaction-type`, `visualization-type`) hold one token or a YAML list: `unit-type: [team, work-system]`.
- **Relations are wikilinks in frontmatter, quoted:** `for-domain: "[[Bakehouse]]"`. Alias: `[[Name|label]]`. A relation field may hold a list unless marked single. Link only to files that exist or that you create in the same step.
- **`member-of` is structure, `contributes-to` is flow.** `member-of` says where an individual or unit sits in the formal structure (*Aufbauorganisation*); `contributes-to` says which higher work system a work system feeds (*Ablauforganisation*). A work system often has both, often the same target (an FL1 work system inside an FL2 one); a plain unit or person has only `member-of`.
- **Locators** (`interaction-of`, `agreement-of`, `mandate-of`, `observes`, `bound-to`) say where something hangs: a board position `"[[Board File]]/col:Column::in"` (slot `::before|in|after`; whole board `#dwsd.board::in`; several boards: `#dwsd.board:<id>/col:…`), a route stage `"[[Route File]]/stage:item @ Band::in"`, or a bare `"[[Entity]]"`.
- **Dates** are ISO: `2026-11-10`, datetimes `2026-11-10T09:00:00`. Do not invent values for fields you do not know; leave them out. Most fields are optional.
- **Work systems and meetings are not types of their own.** A work system is a `unit` with `unit-type` containing `work-system` (it then needs `flightlevel` 1, 2 or 3) and lives in `work-systems/`. A meeting is an `interaction` with `interaction-type: meeting`.
- **Body:** write in the organization's language (read existing files first), as prose. Role, agreement, mandate and decision-record bodies use `##` sections (Purpose, Description, Accountabilities, Decision Rights; Context, Decision, Consequences). The README of an org carries `dwsd-format: "<version>"`.
- **`same-as`** lists the same thing in other systems: `- system: atlassian` plus `id` (stable id) or `url` (browser address); optional `instance`, `label`, `part` (`/lane:X`, `#a-heading`). Not a relation. Identify by `system` + `id`. Reading one to answer is no reason to write it here; write `same-as`, not `sources`.
- **Embedded fences** are plain YAML: `dwsd.board` (visualization with `visualization-type: board`), `dwsd.flightroute`, `dwsd.units`, `dwsd.orgchart`. Their syntax is not in this guide; read the type page of the spec before you write one.

Any entity may also carry: `derived-from`, `tags`, `created_at`, `updated_at`, `created_by`, `same-as`.

## Types

### agreement — `agreements/`
A working agreement, protocol or SLA. Parties and who is responsible for what are in the body.
Required: `agreement-type`.
Fields: `agreement-type` organizational|work; `for-domain` → work-system|role|unit; `agreement-of` locator → work-system|unit|individual; `derived-from` → organizational-decision-record|proposal; `version`; `decision_date` (date); `review_date` (date).

### ai-agent — `ai-agents/`
An AI agent present in the organization, described by where it surfaces (`bound-to`).
Fields: `platform`; `description`; `status` active|deactivated (or other); `for-domain` → work-system|role|unit; `bound-to` locator → work-system|unit|individual.

### driver — `drivers/`
Why to act: a situation, its effect and the need that follows. Comes from insights.
Fields: `for-domain` → work-system|role|unit; `derived-from` → insight; `status`.

### flight-item-type — `flight-item-types/`
A class of work item that flows (a standard order, a feature). Says what the item is, not an instance.
Fields: `uses-route` → flight-route.

### flight-route — `flight-routes/`
How one item type flows through bands and stages. Body holds a `dwsd.flightroute` fence.

### individual — `individuals/`
A person. Pointer, not a personnel file.
Fields: `role` text or → role; `level`; `reports-to` → individual; `member-of` → unit; `position_key`; `external_position_key`.

### insight — `insights/`
Meaning drawn from signals. Ladder: signal, insight, driver, proposal, decision, agreement.
Fields: `observes` locator → any; `title`; `status` new|acknowledged; `acknowledged_at` (datetime); `derived-from` → signal.

### interaction — `interactions/`
People acting together: conversation, bilateral, or meeting (scheduled, bundles interactions with outcomes).
Required: `interaction-type`.
Fields: `interaction-type` meeting|conversation|bilateral (or other); `interaction-of` locator → work-system|unit|individual|visualization; `for-domain` → work-system|role|unit; `start` (datetime); `end` (datetime); `rrule`; `trigger`; `version`.

### mandate — `mandates/`
What a holder must or may do, pulled out into its own file. `for-domain` is the holder.
Fields: `for-domain` → role|unit|work-system; `delegator` → role|unit|work-system|individual; `mandate-of` locator → any; `derived-from` → organizational-decision-record|proposal; `version`; `decision_date` (date); `review_date` (date).

### organizational-decision-record — `decision-records/`
A recorded org design decision (like an ADR): Context, Decision, Consequences.
Fields: `for-domain` → work-system|role|unit; `status` proposed|accepted|superseded|deprecated; `date` (date); `decision-makers` → any.

### proposal — `proposals/`
A proposed response to a driver, before consent. Once consented it produces agreements.
Fields: `derived-from` → driver|insight|signal; `for-domain` → work-system|role|unit; `status` draft|in-consent|consented|declined.

### role — `roles/`
A role held by one or more people; the role persists when people change.
Fields: `role-keeper` → individual; `for-domain` → work-system|unit; `version`; `decision_date` (date); `review_date` (date).

### signal — `signals/`
A selected observation before interpretation.
Fields: `observes` locator → any.

### unit — `units/` / `work-systems/`
Any named grouping (team, department, circle); nestable via `member-of`. With `unit-type` containing `work-system` it is a work system.
Fields: `unit-type` team|work-system (or other); `flightlevel` 1|2|3; `member-of` → unit; `contributes-to` → work-system; `delegator` → any; `version`; `decision_date` (date); `review_date` (date); `term`.

### visualization — `visualizations/`
A picture of a work system. `board` is the kind tools render; other kinds (e.g. `chart`) are plain Markdown.
Required: `visualization-type`.
Fields: `visualization-type` board (or other); `title`; `visualization-of` → work-system.

Rule: a `unit` whose `unit-type` contains `work-system` needs `flightlevel` (1|2|3).

## Minimal examples

`individuals/Jonas Keller.md`
```markdown
---
type: individual
role: "Baker"
member-of: "[[Bakehouse]]"
---
Jonas bakes the morning batch.
```

`roles/Baker.md`
```markdown
---
type: role
role-keeper: "[[Jonas Keller]]"
for-domain: "[[Bakehouse]]"
---
## Purpose
Keeps the bakehouse on schedule.
```

`work-systems/Bakehouse.md`
```markdown
---
type: unit
unit-type: [team, work-system]
flightlevel: 1
member-of: "[[Bakery Operations]]"
---
The team that bakes and dispatches.
```

`agreements/Second Pair of Eyes.md`
```markdown
---
type: agreement
agreement-type: work
for-domain: "[[Bakehouse]]"
agreement-of: "[[Bakehouse Board]]#Bakehouse/col:Review::in"
---
Nothing leaves Review without a second pair of eyes.
```

`interactions/Weekly Planning.md`
```markdown
---
type: interaction
interaction-type: meeting
for-domain: "[[Bakehouse]]"
start: "2026-11-10T09:00:00"
rrule: "RRULE:FREQ=WEEKLY;BYDAY=MO"
---
## Why are we doing this meeting?
To plan the week.
```
